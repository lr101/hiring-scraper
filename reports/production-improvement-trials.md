# Production improvement trials

The implementation started from fetched `origin/main` revision `63cc97a4` and incorporates main’s subsequent `1030d159` saved-source refresh update. Final public-source comparison uses `1030d159` as the baseline; retained changes require a paired public-source trial and regression checks. Work is on the isolated development branch; shared main has not been merged or deployed. The compact [trial artifact](production-improvement-trials.json) records source hashes, selection, frozen labels and predictions. Full source responses and model environments remain local and ignored.

## Successful changes selected

**Complete bounded Lever enumeration.** The public Engel & Völkers board yielded four pages of 100, 100, 100 and 37 distinct IDs on 2026-10-07. Production's first-page adapter returned 100; the shared discovery/refresh reader returns 337: **237 additional postings, a 237% increase on this board**. Every continuation uses the existing public-feed client, request budget and pacing. Ten pages is the bound; reaching it with a full page, duplicate IDs, malformed rows, transport failure or truncation keeps the scan incomplete. Valid earlier pages remain available, and missing jobs cannot close on incomplete scans. A review found a malformed location value could roll back valid earlier rows; that was fixed and verified with real SQLite persistence tests.

Offset pages are not an atomic snapshot. Overlaps observed during enumeration cause incompleteness; undetected concurrent changes remain a provider limitation. Lever refreshes deliberately avoid first-page conditional validators, because an unchanged first-page ETag cannot establish later-page stability. Counts describe source-board coverage, including jobs outside a user's location preferences.

Lever documents public postings and `skip`/`limit` enumeration in its [Postings API](https://github.com/lever/postings-api). Recruitee lists its XML offers feed in the [official API FAQ](https://support.recruitee.com/en/articles/8213076-faq-api).

**Recruitee XML feeds and provider attribution.** Three documented public tenant XML feeds returned 15 offer rows: four from cluetec, two from NEM Energy and nine from virtual7. One cluetec offer is an initiative application; the active-role candidate count is 14. The parser accepts these 14 roles and excludes the initiative application. The tenant canonical `/o/<slug>` route is publicly reachable even where the feed advertises a custom careers domain; tenant attribution must remain explicit.

An actual replay against the current discovery path already finds seven virtual7 WordPress roles. XML yields nine there, rather than nine wholly new jobs. Persisting both produces 16 active rows with different IDs/URLs; available captures do not prove which WordPress and ATS identities are equivalent. Therefore ingestion of a new Recruitee feed is deferred for employers with active legacy HTML jobs. Those existing records remain intact. The accepted current-state gain is **five additional jobs: three cluetec and two NEM**. All 14 XML roles remain available for employers without legacy HTML jobs; virtual7's migration is deferred until explicit aliases can be verified. Source roles across these employers improve from seven to 12 in the guarded legacy discovery/persistence trial, rather than claiming a 14-job increment. Latest main schedules saved-source refreshes without rediscovery: the new adapter is introduced through new/manual discovery or discovery of a company without saved feeds. Existing HTML-only feeds are not automatically migrated to XML by a scheduled refresh.

In a corpus of 120 distinct observed provider URLs, 105 provider/tenant pairs remain unchanged, eight shared infrastructure or utility URLs are rejected, and seven utility-prefixed SmartRecruiters publication URLs are corrected to their explicitly named employers. Fifteen demonstrated false tenant attributions become zero. This is a targeted attribution result; it is not a general company-identification precision estimate.

**Sparse detail evidence.** A cohort was selected from distinct sparse source URLs, sorted by SHA256(URL), with a valid captured HTML response available for offline replay. Of 56 captured pages, the baseline recovered 20 descriptions. The production marker requiring both demonstrated German applicant-section cues recovered 22, retaining all existing successes: **two additional descriptions; 35.7% → 39.3% recovery**. Both new pages are distinct qwertiko junior/senior Linux roles with an exact matching H1. No relaxation of role qualifiers, title identity, overview/fragment rejection or multiple-posting ambiguity is selected. The paired replay preserves all 20 original update dictionaries. Review exposed a dependency: the senior clause requires at least one of bash/Python/Perl/Ruby, but extraction treated Python and Ruby as independent mandatory skills. A bounded correction preserves this explicit list and its general skill evidence while deferring individual hard requirements inside it. Independent required clauses remain enforceable. In constructed profiles against the actual captured role, Python- and Ruby-qualified applicants lose their false mandatory gaps: scores improve from 45/possible to 89/recommended without weight changes. A bash-qualified control improves from 30 to 85. An unknown-scripting control retains missing skill evidence, but is not proved to meet the alternative: hard interpretation is deferred. This narrow German parenthesized form does not resolve every alternative wording. Enrichment version `rules-v14` invalidates stale v12/v13 requirement caches. Unverified alternatives retain a source-backed informational verification unknown; explicit supported alternative evidence resolves it without changing scores or introducing hard gaps. This measures evidence availability, not a proven gain in matching precision.

## Matching experiment rejected for production

The experiment uses 80 source jobs selected by a fixed hash order, excluding 609 IDs or document hashes from all available previous judgments. Independent blind model-assisted review labeled three recommended, six possible and 71 unlikely. Each label is bound to exact title/description SHA256; predictions and methods were frozen before examining labels. The sanitized profile and source snapshot hashes are in the artifact. No tuning followed this evaluation.

| Method | Returned | Relevant recovered | P@10 | nDCG@10 |
| --- | ---: | ---: | ---: | ---: |
| Production rules-v12, eligible score ≥20 | 15 | 4/9 | 0.30 | 0.4172 |
| Fielded alias BM25, eligible top 30 | 30 | 6/9 | 0.30 | 0.2287 |
| Multilingual E5, eligible top 30 | 30 | 7/9 | 0.20 | 0.1871 |
| Candidate union with multilingual cross-encoder | 42 | 9/9 | 0.30 | 0.2685 |

All variants preserve production eligibility. Dense retrieval improves pooled recall from 44.4% to 77.8%, and the candidate union reaches 100%, but the cross-encoder puts relevant results in a worse order than production rules. Its nDCG@10 falls by 0.1487, about 35.6%. **Keep the existing production ranking weights and retrieval approach.** The extraction/cache correction uses rules-v14; all 80 holdout scores and eligibility decisions remain identical to the frozen rules-v12 baseline. The experiment is evidence for a future separate candidate-generation trial, not an accepted ranking change. Recall is within this judged pool; it does not measure market recall. One profile, nine potentially relevant jobs and model-assisted labels cannot establish broad production accuracy.

The frozen encoder is `intfloat/multilingual-e5-small`, using query/passage prefixes, normalized embeddings and maximum cosine over 300-word chunks. The reranker is `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, limited to 384 tokens, over the union of existing rule candidates and top-30 lexical/dense candidates. Benefits are removed from candidate text. The lexical query uses the existing expanded profile query, including all skill names; the semantic query restricts skills to professional evidence. The pre-label lock described the lexical query too narrowly; the artifact records this clarification without changing frozen predictions. Its truncated text and search-relevance training are possible limitations, not demonstrated explanations for failure. Revisions are pinned in [the repeatable optional trial](../experiments/semantic_matching_trial.py). CPU encoding took 39.559 seconds and reranking 29.399 seconds including model loading/download; these are single-run observations, not throughput benchmarks. Experimental packages were installed only in an isolated environment; production dependencies are unchanged.

The [reranker model card](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1) describes multilingual MS MARCO training. Its published retrieval results are not evidence of suitability matching performance; the local comparison above controls this production decision.

Reproduction with the original local jobs requires a separate environment containing CPU torch and sentence-transformers. Run `python experiments/semantic_matching_trial.py --jobs <frozen-local-jobs.json> --profile fixtures/cv_profile.json --labels experiments/fixtures/cv_job_labels/production-holdout-2026-10.json --output <local-predictions.json>`. The tool writes predictions before loading labels and validates document hashes before computing metrics. Exact numeric reproduction can vary with library/hardware versions; frozen original predictions remain in the artifact.

## Company website experiment deferred

All six saved email-domain additions still returned public HTML through the production robots-aware bounded client. Current page identity supports the saved brands, including Autobahn's parent identity and R3DT's XR-EASY redirect. A conservative automatic prototype requiring all distinctive name tokens in title/H1 verifies only Buderus and a3architekten: **2/6 positive leads**. A body substring alone is insufficient to automate attribution to a legal employer or local branch. An independent negative benchmark was unavailable, so no automatic email resolver is promoted. The six manual verifications remain research evidence. No employer entities are merged by domain, brand or proximity.

Unsupported Workday, SmartRecruiters authenticated APIs, Softgarden token APIs, browser automation and external search products remain out of runtime. They have no paired successful integration trial in this work. The demonstrated public API/XML and existing HTML client provide the accepted integration path without a new runtime dependency.

A fresh isolated preview from runtime commit `d0b39f29` is running with its own seeded database.
