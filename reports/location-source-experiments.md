# Location and company-source experiments

**Study date:** 2026-10-05 · **Test location:** Karlsruhe, Baden-Württemberg · **Current code:** [`hiring_scraper/geography.py`](../hiring_scraper/geography.py) and [`experiments/osm_locations.py`](../experiments/osm_locations.py)

This follow-up tests location sources at three different levels: company or establishment candidates, signals that an employer is currently hiring, and geographic boundaries used to filter other sources. These are not interchangeable. A job location is not necessarily an employer office, a tender winner is not necessarily a local employer, and a city centroid is not a street address.

The machine-readable roll-up is [`data/location-sources/summary.json`](../data/location-sources/summary.json). The original request metadata, query URLs, result hashes, and local response bodies are under [`data/location-sources/run-2026-10-05/`](../data/location-sources/run-2026-10-05/). Full response bodies remain gitignored; the derived candidate files below are tracked. The Wikidata homepage crawl and its zero-network cache replay are in [`run-wikidata-career/`](../data/location-sources/run-wikidata-career/) and [`run-wikidata-career-replay/`](../data/location-sources/run-wikidata-career-replay/).

## Additional sources worth adding

These are useful for coverage, but their role differs from OSM and the jobs API:

- **MaStR energy register:** The Bundesnetzagentur says public records include energy units, locations, and operators, and offers XML/CSV data plus a daily full export. The current download page listed a **3,144,319 KB** public XML export, too large for this POC to fetch. The SOAP web service requires a registered user/key. This is a promising niche lead source for energy companies and facility operators with real locations, not a general company list. See the official [MaStR data download](https://www.marktstammdatenregister.de/MaStR/Datendownload) and [web-service documentation](https://www.marktstammdatenregister.de/MaStRHilfe/subpages/webdienst.html). I evaluated the docs and metadata, but did not download the multi-gigabyte file or create an account.
- **Destatis GENESIS / Unternehmensregister statistics:** Table [52111-0006](https://genesis.destatis.de/datenbank/online/statistic/52111/table/52111-0006/) provides establishment counts by state, year, industry, and employment-size band. It is a good denominator for asking whether a discovery list is implausibly small, but it contains counts rather than company leads. The [GENESIS API](https://github.com/StatistischesBundesamt/GENESIS-Online) requires a registered account; I did not make an authenticated request.
- **Google Places Nearby Search:** A paid source that natively searches circles from 0 to 50 km and can return place names and website URIs. It requires an API key and billing, and website fields raise the applicable SKU. I did not make a billable request. Google also warns that results are ranked and some nearby places may not appear, so it should be a comparison/enrichment source rather than assumed-complete ground truth. See [Nearby Search](https://developers.google.com/maps/documentation/places/web-service/nearby-search) and [usage and billing](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing).
- **CORDIS / EU-funded project partners:** CORDIS’s European research knowledge graph describes participant organizations and their sites; this could surface research-heavy firms missed by map categories. The REST extraction API requires registration/key, while CORDIS also publishes linked data and bulk datasets. I did not run a location query, so treat this as the next sector-specific source to test. See [CORDIS Datalab](https://cordis.europa.eu/datalab) and its [SPARQL guide](https://www.cordis.europa.eu/about/sparql/en).
- **IHK, municipal and university directories:** These can provide homepages and local relevance, as the existing [KIT directory sample](../data/karlsruhe/kit_candidates.csv) did, but each directory has its own format, scope, and access rules. I found no single cross-Germany API for these directories. Treat them as region adapters, not a uniform source.
- **Common Crawl and web search:** Common Crawl can expose historical paths and subdomains; the earlier [career-page experiments](career-discovery-improvements.md) found path ideas but did not make it a dependable live company finder. A documented search API can also find employer career subdomains and links, then the company-site crawler should verify ownership and current content.

## Linking a company to its own hiring site

For sources that return a company homepage, the most reliable chain tested so far is:

1. Keep the source name, homepage, coordinates/address, and provenance as a candidate. Do not treat a result as a company until its identity and location are checked.
2. Fetch the homepage and inspect visible navigation/footer links, robots-permitted sitemaps, structured `JobPosting`/`DataFeed` content, and links to known ATS providers. Follow only a small, ranked number of links.
3. Store the employer’s own career URL separately from the ATS vendor URL and the job-board/feed URL. A branded subdomain or a vendor path counts as a verified link only when the employer site links to it or equivalent ownership evidence exists.
4. Parse the public board feed where supported. Otherwise record “provider identified, feed unsupported” instead of implying that no jobs exist.

The 11-company Wikidata sample was intentionally selected, not random. A six-page-per-company, robots-aware run verified career content for **6 of 11** homepages; five remained unresolved. It made 88 live requests once; the final-code replay reused all 88 captures and made **zero** new requests. Examples include [Schoeps jobs](https://schoeps.de/ueber-uns/jobs-praktika.html), [PTV Group careers](https://careers.ptvgroup.com/en/jobs/?filter%5Bclient_id%5D%5B%5D=2), [PI careers](https://www.physikinstrumente.com/en/about/careers), [Storch und Beller jobs](https://storch-beller.de/startseite/karriere/jobs/), and [Volksbank pur careers](https://www.volksbank-pur.de/meine-bank/karriere/uebersicht.html). PTV is a good example of a company homepage linking to a separate careers host. Volksbank pur linked to a Helix-hosted board; the crawler recognized Helix but did not parse its jobs. No structured feeds were parsed in this sample.

“Unresolved” is not “no hiring page.” Produktivkeller’s robots response was unavailable; SciMo/BOKELA/CAS had incomplete or 404 fallback paths; Moninger’s `/jobs/` URL redirected to an age-confirmation page that contained no hiring content. The crawler stopped there and kept the result unresolved. The test also caught a legal-news article being mistaken for a career page because it mentioned employers and applications; the classifier now excludes news/publication paths, with a regression test. The corrected replay is in [`run-wikidata-career-replay/companies.csv`](../data/location-sources/run-wikidata-career-replay/companies.csv). For the earlier live comparison of Greenhouse, Lever, Personio, Ashby, Schema.org feeds and detection-only ATS links, see the [career discovery improvements report](career-discovery-improvements.md).

## City radius, state, and precision

The new CLI accepts a city name and radius, explicit latitude/longitude and radius, or a German state. City mode geocodes one result with Nominatim; the radius is around that point, not around the municipal boundary. Candidate points are post-filtered with a great-circle distance because Overpass may return a way/relation whose center falls outside the circle. State mode builds an administrative-area Overpass query, but the live state test timed out, so it is an experiment rather than the recommended statewide path.

For production, keep these fields distinct:

- `company_location`: address/point and its source;
- `location_precision`: street/point, locality, state-only, or city-centroid;
- `location_role`: headquarters, branch/site, facility, or job location;
- `distance_m` from the selected city center, where a real point exists;
- `state_code`/state name assigned from the BKG polygon;
- `career_url`, `ats_board_url`, and `job_feed_url`, each with evidence and last-checked time.

For a city radius, local OSM or a paid Places API can seed addresses. For a state, select the state polygon, use a state extract locally, and assign points from all sources to that polygon. Query the BA API for current hiring signals in parallel. Add Wikidata, TED, CORDIS, MaStR, and regional directories as supplemental cohorts, then deduplicate by normalized domain and company/address evidence. Keep job locations separate from company locations so “a company hires near Karlsruhe” does not accidentally become “the employer is headquartered near Karlsruhe.”

## Code and validation

`hiring_scraper/geography.py` now normalizes German state names, builds Overpass circle/state queries, parses Nominatim city results, filters OSM points by distance, and assigns WGS84 points to BKG polygons. `experiments/osm_locations.py` accepts `--city` plus `--radius-m`, `--lat/--lon` plus radius, or `--state`; it writes the query, response metadata, normalized CSV/JSON, and a completeness summary. The direct script launch and `--help` work. Unit tests cover state aliases, coordinate bounds, point-in-polygon holes/multipolygons, geocoder validation, and radius distance.

The next highest-value test is a stratified Karlsruhe/BW sample from a local Geofabrik extract, joined against BA, the current OSM set, CORDIS, and regional directories. Label each row “verified company,” “verified own career page,” “parsed public jobs,” “unresolved,” and location precision separately. That will measure incremental coverage without treating the best-looking source’s own candidate count as ground truth.
